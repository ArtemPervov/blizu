# Панель оператора

Адрес: `/operator`. Разрешение оператора хранится отдельно от роли заказчика, исполнителя или арбитра. Одна учётная запись может иметь прежнюю роль и дополнительный доступ к панели. Публичная регистрация не выдаёт это разрешение.

## Возможности

- Обращения: жалобы на предложения и аккаунты, фильтры по состоянию, поиск, рассмотрение или отклонение с объяснением. При рассмотрении можно скрыть предложение либо заблокировать аккаунт — в той же транзакции, что и решение. Повторное рассмотрение закрытого обращения отклоняется. Отправитель получает ответ в уведомлениях сервиса.
- Пользователи: поиск по имени, email, городу и ID; блокировка и восстановление доступа, установка и снятие отметки профиля исполнителя.
- Предложения: поиск, просмотр, скрытие и снятие скрытия с обязательной причиной. Отдельно видно, если заблокирован автор.
- Журнал: кто, когда, какой объект изменил, причина и состояние до/после. Действия серверного provisioning/CLI отмечаются как серверные. Пароли и сессии в журнал не записываются.
- Сводка: пользователи, блокировки, опубликованные и скрытые предложения, очередь обращений. Все списки имеют серверную пагинацию и фильтры в URL.

Арбитраж заказов остаётся функцией роли арбитра. Само разрешение оператора не открывает чужие диалоги заказов или фото к коммерческим спорам. Если сотруднику нужны обе функции, выдайте разрешение существующей учётной записи арбитра через серверную команду.

## Вход в демонстрационной среде

При `ENABLE_DEMO=true` в окне входа есть кнопка **Оператор**. После входа откройте `/operator` или пункт панели в меню аккаунта. Демо-оператор создаётся и при обновлении уже существующей демонстрационной базы. Данные и изменения в демо сохраняются.

## Создание в Portainer

Укажите в окружении стека оба значения:

```dotenv
OPERATOR_EMAIL=operator@your-domain.me
OPERATOR_PASSWORD=
```

Пароль задайте самостоятельно: 12–128 символов. Email должен отличаться от уже зарегистрированных аккаунтов, включая `ADMIN_EMAIL`, если вы создаёте отдельного сотрудника. При запуске API создаст новый аккаунт и разрешение оператора. Повторный запуск не меняет существующий пароль. Оба Compose-файла передают эти переменные в API; по умолчанию они пустые и доступ не создаётся.

Если email принадлежит существующему аккаунту без разрешения, startup не повышает его привилегии и сообщает об ошибке. Для такого аккаунта используется явная команда выдачи доступа ниже.

После первого создания можно очистить **обе** переменные bootstrap и перезапустить стек: аккаунт и разрешение сохраняются в томе `blizu_data`. Это также позволит позже отзывать доступ без конфликта с сохранённой настройкой первоначального создания.

## Выдать доступ существующему аккаунту

На Docker-хосте, из каталога проекта:

```bash
docker compose exec -e OPERATOR_EMAIL=existing@example.com api node dist-server/server/operator-account.js grant
```

В Portainer тот же `node dist-server/server/operator-account.js grant` можно выполнить в консоли контейнера API, предварительно задав `OPERATOR_EMAIL` нужного существующего аккаунта. Для grant пароль не требуется; действие доступно только владельцу серверного окружения. Заблокированному аккаунту разрешение не выдаётся: сначала снимите блокировку.

Отзыв доступа:

```bash
docker compose exec -e OPERATOR_EMAIL=existing@example.com api node dist-server/server/operator-account.js revoke
```

Обе команды завершают действующие сессии. После выдачи доступа сотрудник входит заново. Через панель нельзя выдавать или отзывать разрешения операторов, менять бизнес-роль или блокировать операторские аккаунты. Серверная команда revoke может отозвать и последнее разрешение; для восстановления используется grant на сервере.

В локальной разработке доступны `npm run operator:create`, `npm run operator:grant`, `npm run operator:revoke`. Они читают `OPERATOR_EMAIL`, а create — также `OPERATOR_PASSWORD` из `.env` или окружения. На Windows используйте `npm.cmd`. В production-образе используйте скомпилированный JS, как в командах выше: tsx и исходники TS туда не включены.

## Последствия модерации

Блокировка удаляет действующие сессии и запрещает новый вход. Предложения и открытые заявки участника исключаются из публичной выдачи; его отклик нельзя выбрать для нового заказа. Заказы и история не удаляются. После разблокировки требуется новый вход. Отдельно скрытые предложения автоматически не восстанавливаются.

Скрытое предложение не возвращается публичным каталогом, избранным и прямым запросом карточки. Автор и оператор могут просмотреть его с пометкой и причиной. Автор получает уведомление; гостевое избранное, недавнее и открываемое сравнение проверяют сохранённые записи по текущим данным API. Уже загруженные клиентом данные физически не стираются из истории браузера; списки обновляют доступность при открытии и периодически.

Все изменения модерации и запись журнала выполняются в транзакции. Структура SQLite обновляется до версии 3 при запуске без перестройки таблицы пользователей и без удаления прежних записей и сессий. Версия 2 добавила модерацию, версия 3 — происхождение внешних объявлений. Перед обновлением production сделайте обычную резервную копию тома по [инструкции](../README.md).

Проверка разрешений в API и фиксация изменений соответствуют выбранному подходу минимальных полномочий: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). Это описание реализации, а не заявление о полной сертификации безопасности.
